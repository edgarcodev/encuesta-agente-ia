# AGENTS.md

## Stack (verify before assuming anything)

- **Build step:** `esbuild` via `npm run build`. Produces `dist/` with bundled + minified assets. Deployed to Vercel with `"outputDirectory": "dist"`.
- **Frontend source:** `index.html`, `styles.css`, `app.js` (vanilla HTML + CSS + JS). The JS renders a landing page or survey steps based on `?tipo=` URL parameter.
- **Frontend output:** `dist/index.html`, `dist/styles.css`, `dist/app.js`, `dist/images/`, `dist/config/preguntas/` — generated by `build.mjs`.
- **Backend:** `api/encuesta.js` — a Vercel serverless function (default export `handler(req, res)`). It proxies `POST` body to Supabase table `respuestas_encuesta` using `SUPABASE_SERVICE_KEY`.
- **Database:** Supabase. Table `respuestas_encuesta` stores `{ datos }` JSONB plus a `tipo_encuesta` column.
- **DB schema migrations:** live versioned in `supabase/migrations/NNNN_name.sql` (schema only — never data fixes). Each migration must be applied **exactly once** to the production SQL editor; the files deliberately avoid `if not exists` so a re-run fails loudly. They are also recorded in `supabase_migrations.schema_migrations` when applied via the MCP/CLI. Today: `0001_rate_limits.sql` (SPEC 03, `rate_limits` table + `increment_rate_limit` RPC) and `0002_tipo_encuesta.sql` (SPEC 08, `tipo_encuesta` column + CHECK constraint).
- **Static source:** `images/megaremates.svg` (logo) → copied to `dist/images/` on build.
- **Reference template:** `references/vendedores/` mirrors the same structure (`index.html`, `api/encuesta.js`, `vercel.json`) for adding more survey types (vendedores, proveedores).

## Environment (will break silently if missed)

- `.env` is **gitignored** and contains real Supabase credentials (`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `SECRET_NONCE`).
- `.env.example` exists but uses `echo` commands (not a standard dotenv template).
- In production these must be set in the **Vercel dashboard → Settings → Environment Variables**, not from a local file.
- Locally: create `.env` with the three variables above before testing the API function.

## Vercel routing gotcha (high-impact, easy to miss)

`vercel.json` currently has rewrites for API, login, dashboard, and a catch-all:

```json
{
  "rewrites": [
    { "source": "/api/(.*)", "destination": "/api/$1" },
    { "source": "/login/(.*)", "destination": "/login/$1" },
    { "source": "/login", "destination": "/login/index.html" },
    { "source": "/dashboard/(.*)", "destination": "/dashboard/$1" },
    { "source": "/dashboard", "destination": "/dashboard/index.html" },
    { "source": "/(.*)", "destination": "/" }
  ]
}
```

**Always place specific rewrites (API, login, dashboard) before the catch-all.** The catch-all must be last.

## Security gotchas (do not ignore)

- `api/encuesta.js` uses `SUPABASE_SERVICE_KEY` which **bypasses RLS** (full admin access). It validates `token` by **exact equality against `process.env.SECRET_NONCE`** and fails closed (500, nothing saved) if that variable is missing or empty. The secret's value is embedded in `index.html` as `const NONCE` (public by design, SPEC 02); rotating it requires updating three places at once: `.env`, the Vercel dashboard, and `index.html`.
- **Rate limiting: 5 POST / 10 min per IP** (SPEC 03). Every POST — including invalid tokens and bad payloads — calls the PostgREST RPC `increment_rate_limit(p_ip)` *before* the token check; a persistent counter lives in the `rate_limits` table (one row per IP, fixed window). When `count > 5` the API answers `429` with a `Retry-After` header. The limit itself is `const RATE_LIMIT_MAX = 5` in `api/encuesta.js`; the SQL function only counts. The RPC fails **open** (`console.error` and continue) because `SECRET_NONCE` remains the real gate. IP source: `x-real-ip` (set by Vercel, not spoofable) → first entry of `x-forwarded-for` → `'unknown'`. No CAPTCHA, no schema validation on `datos`.
- Frontend calls `https://ipapi.co/json/` on load without user consent (privacy/GDPR concern).

- Use `/spec <feature>` to design a spec (Phase 1–4, saves to `specs/`), then `/spec-impl <NN-slug>` to implement an **Approved** spec on a git branch.

## Build

- **`npm run build`** — runs `build.mjs`, which bundles and minifies `styles.css` → `dist/styles.css` and `app.js` → `dist/app.js` (IIFE format) using esbuild's JS API, copies `index.html`, `images/`, and `config/preguntas/` to `dist/`, and cleans `dist/` before each run.
- **`npm run vercel-build`** — alias to `npm run build`, invoked by Vercel's build hook before serving `dist/` (configured via `"outputDirectory": "dist"` in `vercel.json`).
- **`dist/`** — build output folder. Contains the production-ready static assets. Committed neither to git (in `.gitignore`). Never edit files in `dist/` directly — they are overwritten on every build.

## Commands

- **`npm run build`** — generates `dist/` locally.
- **`npm install`** — installs `esbuild` (only devDependency).
- There are **no test/lint scripts**. Verification is manual:
  - Open `index.html` in a browser to test the survey frontend (source files, no build needed).
  - Open `dist/index.html` to test the bundled output.
  - Deploy to Vercel (or use Vercel CLI) to test `api/encuesta.js`; local execution of the serverless function requires the Vercel runtime or a compatible fetch shim.

## Data model

Table `public.respuestas_encuesta`:

| Column | Type | Nullable | Notes |
|--------|------|----------|-------|
| `id` | bigint | no | PK (auto) |
| `datos` | jsonb | no | Survey answers + metadata |
| `tipo_encuesta` | text | yes | CHECK IN ('compradores', 'vendedores', 'proveedores'). Hardcoded by each survey frontend, validated by the API. Historical records may have NULL (no backfill). |
| `created_at` | timestamptz | no | Auto-inserted |

POST body format: `{ datos, token, tipo_encuesta }`.

## Multiple surveys — `?tipo=` parameter (SPEC 09 + 12)

`app.js` reads `?tipo=` from the URL. **No default type** — without `?tipo=`, the landing page is shown. If the type is valid, splash → survey loads. If invalid, an error message appears.

The `ENCUESTAS` object in `app.js` maps each type to its configuration:

```js
ENCUESTAS = {
  compradores: { tipo, titulo, endpoint, color, STORAGE_KEY, NONCE|NONCE_KEY, questionsUrl },
  vendedores:  { tipo, titulo, endpoint, color, STORAGE_KEY, NONCE|NONCE_KEY, questionsUrl },
  // proveedores: ... (future — add here when ready)
}
```

- **tipo** — the value sent as `tipo_encuesta` in the POST.
- **titulo** — shown in `<h1>` and splash screen.
- **endpoint** — API endpoint to POST to (default `/api/encuesta`).
- **color** — progress bar gradient color.
- **STORAGE_KEY** — localStorage key for "already submitted" check.
- **NONCE** — fixed token string, **or** **NONCE_KEY** — sessionStorage key for dynamic nonce generation.
- **questionsUrl** — path to the JSON file with questions.

### Adding a new survey type

1. Add a new entry to `ENCUESTAS` in `app.js` with its own `questionsUrl`.
2. Create `config/preguntas/<new_type>.json` with the question definitions.
3. If the type is not yet in the DB CHECK constraint, create a migration to update `chk_tipo_encuesta`.
4. Each survey type accesses its own URL: `/?tipo=newtype`.
5. The `references/` folder templates are still useful as a starting point for new survey HTML+API.

## Question JSON format (SPEC 10)

Questions live in `config/preguntas/<tipo>.json`. Each question is a JSON object:

```json
{
  "id": "p1",
  "question": "1. ¿Pregunta?",
  "type": "checkbox|radio|text|textarea",
  "options": ["Opción 1", "Opción 2"],
  "allowOther": true,
  "maxSelections": 3,
  "placeholder": "...",
  "hint": "...",
  "condition": { "always": true },
  "dynamicDefinition": { ... }
}
```

**Conditions** (no eval, declarative only):

```json
{ "always": true }
{ "field": "p9", "operator": "oneOf", "value": ["Sí", "No"] }
{ "field": "p13", "operator": "notIncludes", "value": "No he tenido..." }
{ "logic": "and", "conditions": [...] }
```

Operators: `equals`, `notEquals`, `oneOf`, `includes`, `notIncludes`.

**Dynamic definitions** (questions that change type/options based on another answer):

```json
{
  "dynamicDefinition": {
    "logic": "and",
    "conditions": [
      { "field": "p21", "operator": "equals", "value": "Perú" },
      { "field": "p23", "operator": "oneOf", "value": ["En el mismo país...", "Mi actividad se desarrolla..."] }
    ],
    "then": { "type": "radio", "options": [...], "allowOther": true },
    "else": { "type": "text", "placeholder": "..." }
  }
}
```

## Authentication (SPEC 13)

`/login` uses Supabase Auth (email/password) for admin access.

- **Client:** `@supabase/supabase-js` loaded via CDN in `login/index.html` and `dashboard/index.html`.
- **Login:** `login/auth.js` handles `signInWithPassword()`, error mapping, and redirect to `/dashboard`.
- **Dashboard protection:** `dashboard/dashboard.js` checks `getSession()` on load; redirects to `/login` if no session.
- **Logout:** `signOut()` → redirects to `/login`.
- **Session persistence:** localStorage (Supabase default).

### Variables de entorno

| Variable | Uso | Dónde |
|----------|-----|-------|
| `SUPABASE_URL` | URL del proyecto | `api/encuesta.js` (server), `login/auth.js` (client), `dashboard/dashboard.js` (client) |
| `SUPABASE_ANON_KEY` | Publishable key | `login/auth.js` (client), `dashboard/dashboard.js` (client) |
| `SUPABASE_SERVICE_KEY` | Service role key (bypasses RLS) | `api/encuesta.js` (server only) |

**Important:** `SUPABASE_ANON_KEY` is embedded in `login/auth.js` and `dashboard/dashboard.js` for now. In production, set it as a Vercel environment variable and inject it during build or use runtime config.

### Setup

1. Enable Email provider in Supabase Dashboard → Authentication → Providers.
2. Disable email confirmation in Supabase Dashboard → Authentication → Settings (for dev).
3. Create admin user in Supabase Dashboard → Authentication → Users.
4. Set `SUPABASE_ANON_KEY` in Vercel dashboard (Settings → Environment Variables).

## Row Level Security (SPEC 15)

RLS is enabled on `respuestas_encuesta` and `respuestas_encuesta_vendedores`.

| Policy | Table | Role | Operation | Condition |
|--------|-------|------|-----------|-----------|
| `authenticated_read` | `respuestas_encuesta` | `authenticated` | SELECT | `auth.uid() IS NOT NULL` |
| `authenticated_read` | `respuestas_encuesta_vendedores` | `authenticated` | SELECT | `auth.uid() IS NOT NULL` |
| `Permitir inserciones publicas` | `respuestas_encuesta` | `anon` | INSERT | *(existing — survey submissions)* |

**Key points:**
- `service_role` bypasses RLS automatically — `api/encuesta.js` is unaffected.
- `anon` can only INSERT (submit surveys), cannot SELECT.
- `authenticated` users can SELECT (read dashboard data).
- No UPDATE/DELETE policies yet — coming in future specs.

**Verify policies:**
```sql
select policyname, roles, cmd from pg_policies where tablename = 'respuestas_encuesta';
```
